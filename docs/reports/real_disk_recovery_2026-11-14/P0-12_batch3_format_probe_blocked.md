# P0-12 批次 3 引擎格式探测：被媒体坏带阻断

- 日期：2026-11-15 09:39:25 – 10:28:26（运行 49 分 01 秒，主动终止）
- 目的：补齐批次 3（vol boot LBA 209728638）105,901 个节点缺失的逐文件引擎签名格式判定
- 结论：**未能完成。阻断原因是源盘出现连续不可读带，不是引擎缺陷。**

## 一、实际执行

纯引擎，无脚本参与判定：

```
phoenix_headless_p07.exe scan --disk 2 --boot 209728638 \
    --ids batches\batch_003_ids.txt \
    --format-sample 0 --format-probe-bytes 4096 \
    --out engine_fmt_b003.csv
```

`scan` 的链路是 `NtfsParser::Open` → `ScanMetadata` → `GetAllFiles` → 按 ids 过滤 →
`RecoverEngine::ReadFileDataPrefix()` → `SignatureDB::Match(AC)` →
`FormatPayloadScoreUtil::Score`。只读，不写源盘。

## 二、现场观测

从 09:43:18 起，引擎持续报同一类错误，每 149.5 秒一条，LBA 严格连续递增：

| 序号 | LBA | err | 时间 |
|---:|---:|---:|---|
| 1 | 216020094 | 121 | 09:43:18 |
| 2 | 216020095 | 121 | 09:45:48 |
| … | … | 121 | … |
| 18 | 216020111 | 121 | 10:25:40 |

- `err=121` = `ERROR_SEM_TIMEOUT`，设备层读超时，**不是重试次数耗尽**。
- 间隔恒定 149.5 s，18 个扇区共耗 42 分 22 秒。
- 坏带起点字节偏移 = 216020094 × 512 = **110,602,288,128 B ≈ 103.0 GiB**。
- 坏带长度 **未知**：观测窗口内从 094 连续递增到 111 未见终止。
- **全程未生成任何 CSV**（`engine_fmt_b003.csv` 不存在），即引擎在发现/枚举阶段就卡住，
  根本没走到逐节点前缀探测——这意味着不仅是那 105,901 个 id，**整个卷的重新扫描当前都无法完成**。

## 三、引擎行为核对（源码级）

`disk/SectorReader_win.cpp` `ReadSectors()`：

1. 先 `TryRead` 整段；失败后进入逐扇区慢路径（这段逻辑本身是对的）。
2. 每个扇区按 `ReadPolicy.maxRetries = 3` 重试，`timeoutMs = 8000`、`retryDelayMs = 50`。
3. 仍失败则 `m_badSectors.MarkBad(lba)`、`LOG_WARN(BAD SECTOR)`，
   `skipBadSectors = true`（默认）下 `memset` 零填充后**继续**。

所以引擎没有死锁、没有崩溃、也没有静默跳过：它在正确降级。问题是
`maxRetries=3 × timeoutMs=8000` 名义上界是 32 s/扇区，实测 149.5 s——
真正计时的是系统/驱动的 SCSI 超时（`err=121`），引擎自己的 8 s 等待并不能约束它。
`phoenix_headless` 也没有把 `ReadPolicy` 暴露成命令行参数（见 `main()` 的 usage），
因此无法从外部把单位代价压下来。

按 149.5 s/扇区推算：坏带若为 1,000 扇区则需 41.5 小时，10,000 扇区需 17 天。
在长度未知的前提下继续跑没有工程意义，且会持续压测一块正在失效的盘，
因此 10:28:26 主动终止。

## 四、这说明了什么

1. **这块盘正在恶化（或有此前未触达的坏区）。** P0-6 阶段同卷两次扫描均记录
   `badSectors = 0` 并正常完成；本次同一条链路在 103 GiB 处遇到连续不可读带。
   在 P0-6 与 P0-12 之间，介质状态发生了变化。
2. **已完成的恢复与字节验证不受影响。** 878,373 个唯一节点的数据是在更早、盘况更好时
   读出的，且与独立 MFT 真值逐字节比对通过（`unresolved = 0`）。
   批次 3 的 105,901 个文件当时 105,901/105,901 有效验证通过——
   若其载荷位于这条坏带内，当时就不可能通过 SHA-256 比对。
3. **缺口性质改变。** 批次 3 的格式判定留痕从「引擎没做」变成
   「引擎现在做不了，因为介质读不出来」——这是硬件边界，不是引擎能力边界。

## 五、仍未闭合

- 批次 3 的 105,901 个节点的逐文件 `engineExt / formatAgreement / formatScore` 仍缺。
- 坏带的起止范围未测绘（测绘本身每个扇区要 149.5 s，代价高昂）。
- `final_audit.py` 的格式门禁目前仍只覆盖批次 ≥ 4（762,629 行）与 vol63（9,855 个，P0-6 全量）。

## 六、若要继续，唯一可行方向

不改引擎的前提下，`ReadPolicy` 需要可调（把 `maxRetries` 降到 0、并让 `timeoutMs`
真正约束 `ReadFile` 的 overlapped 等待），否则每个坏扇区固定 149.5 s，
无法在有生之年扫完一条未知长度的坏带。这属于引擎改造（`disk/SectorReader_win.cpp` +
`tools/phoenix_headless.cpp` 参数透出），在拿到坏带范围之前不建议动手。
