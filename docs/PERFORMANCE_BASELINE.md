## 8. 并行 RAW 扫描吞吐基准（A1-11，2026-11-08 实测）

> 本节填补此前「真实全盘提速基准未量化」中的**合成镜像吞吐**部分。注意：这仍是**受控合成基准**，**不是真实磁盘/真实卷的端到端提速**，不得对外表述为「真实全盘提速 5 倍」。

### 8.1 环境与口径

| 项目 | 值 |
|---|---|
| 编译器 / 构建 | MinGW g++ **7.3.0**，`CMAKE_BUILD_TYPE=Release`（`-O3 -DNDEBUG`），`PHOENIX_BUILD_GUI=OFF` |
| 逻辑核数 | `std::thread::hardware_concurrency()` = **32** |
| OS | Windows x64 (`SectorReader_win.cpp`) |
| CPU 型号 / RAM / 磁盘型号 | **未采集**（本机未记录，勿据此做跨机对比） |
| 镜像 | **256 MiB**（268,435,456 B / 524,288 扇区）合成 `.dd`；常量 `0x5A` 填充 + 每 256 KiB 植入 1 个 header-only graphic magic（png/jpg/gif 轮换），共 **1023** 个；每个刻出段恰为 `[本, 下一)`，无嵌套 |
| 计时 | `std::chrono::steady_clock` 包住整次 `Run()`（含 reader 打开、DB 构造、扫描、合并、全局 pass）；每个线程数重复 **3** 次取**中位数**；吞吐 = 256 MiB / 中位耗时 |
| 等价性 | 每次运行都与一次未计时串行 warm-up 的 `(rawOffset, ext, size)` 集合比对 |

**方法学修正（重要）**：首版按 `1→2→4→8` 顺序测量，刚写入的 256 MiB 文件后台回写使**前几个配置偏冷**，曾得到 1T=2246 ms / 8T=266 ms 的 8.44x 虚高结果。现工具在写盘后执行 `_commit`（强制回写）+ 整文件预读 + 2 次未计时串行 warm-up，并在每轮重复中**旋转线程数顺序**消除先后偏差。修正后两种入口的 1T 基线一致（1352.6 / 1357.1 ms），独立复测亦稳定。

### 8.2 实测结果

**RUN A — `RawScan::Run` 直连**

| 线程数 | 中位耗时 (ms) | 吞吐 (MB/s) | 加速比 | 发现文件 | 文件集一致 |
|---|---|---|---|---|---|
| 1（串行基线） | **1352.6** | 189.3 | 1.00x | 1023 | yes |
| 2 | 718.1 | 356.5 | **1.88x** | 1023 | yes |
| 4 | 416.7 | 614.3 | **3.25x** | 1023 | yes |
| 8 | 271.4 | 943.3 | **4.98x** | 1023 | yes |

**RUN B — `CarveModuleService::Run`（A1-10 生产配置链）**

| 线程数 | 中位耗时 (ms) | 吞吐 (MB/s) | 加速比 | 发现文件 | 文件集一致 |
|---|---|---|---|---|---|
| 1（串行基线） | **1357.1** | 188.6 | 1.00x | 1023 | yes |
| 2 | 722.8 | 354.2 | **1.88x** | 1023 | yes |
| 4 | 424.7 | 602.8 | **3.20x** | 1023 | yes |
| 8 | 274.7 | 932.0 | **4.94x** | 1023 | yes |

两种入口差异 **< 2%**，说明 A1-10 的配置链（`UnifiedScanConfig` → `MakeCarveConfig` → `CarveConfig` → `SetThreadCount`）本身没有可测开销；所有配置下 `file-set equivalence vs serial: PASS`。

### 8.3 解读与边界

- 2T/4T 接近线性（1.88x / 3.25x），8T 降到 4.98x：符合 Amdahl 预期——`RescanNestedGraphicHeaders`、`AddFragmentNodes`、按 `rawOffset` 合并、以及每线程 `SectorReader::OpenImage` + `SignatureDB` 克隆仍在主线程串行完成；固定 128 扇区/块且无动态负载均衡。
- **不得夸大**：① 合成低熵填充**不含随机假阳性 magic**，真实磁盘的误报/漏报与 carving 代价未量化；② 文件为 OS 页缓存中的普通文件，**非真实物理盘 I/O**，也未含坏扇区重试；③ 所有 magic 严格递增，刻意规避了已知的「嵌套 jpeg 跨 chunk cursor 跳过」分叉点；④ 测的是 RAW 雕刻流水线吞吐，**不是 GUI 端到端扫描耗时**；⑤ CPU / 内存 / 磁盘型号未记录，**不可跨机比较**，也不作为发版门禁。
- **仍未量化**：真实 10–50 GB 卷、碎片化镜像、随机假阳性负载、坏扇区场景；峰值 RSS；`DeepScan` 回退路径在多核下的耗时。

## 9. RAW 雕刻误报率基线（W5 / CAR-002，2026-11-08 实测）

> 首次量化 `PRODUCT_SCOPE_SCAN_RECOVER_REPAIR.md §7 #13` 的 CAR-002「雕刻误报率未量化」。与 §8 不同，§8 用常量 `0x5A` 填充、**刻意不含随机假阳性**；本节改用 seeded 随机噪声并提供已知真值。

### 9.1 环境与口径

| 项目 | 值 |
|---|---|
| 测试 | CTest `RawScanFalsePositive`（`tests/test_rawscan_false_positive.cpp`），8 项断言全绿 |
| 工具链 | MinGW g++ 7.3.0 / Release；另在 GCC 14.2.0 构建校验 |
| 镜像 | **8 MiB**（16384 扇区），`std::mt19937` seed `12648430`（0xC0FFEE）逐字节随机填充 |
| Case A | **零植入** → 每个报告项都是假阳性 FP；重复两次验证 FP 集确定性 |
| Case B | 同一噪声 + **16** 个 512 对齐 header-only magic（jpg/png/gif，含 chunk 边界扇区） |
| 指标 | TP / FP / FN、precision、recall、FP per MiB |
| 门禁 | `TP == 16`、`FN == 0`、`recall >= 99%`、FP 集可复现；**首次测量不设 FP 硬阈值** |

### 9.2 实测结果

| Case | 报告文件数 | TP | FP | FN | precision | recall |
|---|---|---|---|---|---|---|
| A（纯噪声，两次重放一致） | 115 | — | **115（14.38 FP/MiB）** | — | 0% | — |
| B（噪声 + 16 植入） | 125 | **16** | 109 | **0** | **12.80%** | **100.00%** |

原始输出：`docs/reports/rawscan_false_positive_2026-11-08.txt`（含 CSV 行，可直接导入）。

### 9.3 结论与边界（不得夸大）

- **首次得到可复现的误报率**：高熵随机数据下约 **14.4 个假阳性 / MiB**，精确率仅 **12.80%**。当前 header-only 图形签名 + 回退 carver 在随机字节上误报显著，真实卷（压缩流、加密区、空闲区随机数据）需分层复测。
- recall 100% 只证明「植入 magic 不漏」，**不代表真实文件恢复成功率**；TP 是 magic 命中，不是可打开的文件。
- Case A 的 115 与 Case B 的 109 不同：植入覆盖了噪声中的偶然 magic 并改变 carver 边界，属预期行为。
- 本节是**基线测量而非质量门禁**，故不设 FP 上限；后续 `footer`/`secondary` 约束、`AssessRawStructure` 调参应以本节为对照。
- 8 MiB 合成随机镜像，非真实磁盘 / 真实卷 / GUI 端到端；不含碎片化、坏扇区、真实压缩流；不可与 §8 的吞吐数据混用口径。

## 10. 真实损坏卷端到端恢复基线（2026-11-14，进行中）

> **状态：进行中。** 本节记录 6 批中已完成的第 1–2 批（卷 0 全量）；批次 3–6 完成后须重新汇总。完整逐批记录见
> `docs/reports/real_disk_recovery_2026-11-14/summary.md`（由 `tools/make_summary.py` 自动生成）。

### 10.1 环境与口径

| 项 | 值 |
|---|---|
| 源盘 | `\\.\PhysicalDrive2` ST1000DM003-1CH162 / 931.51 GiB / SCSI-USB 桥接 / 2 个 `0x42` LDM 动态分区 / 系统未组装卷 |
| 文件系统 | 两个 NTFS 卷（boot LBA 63 / 209728638），4096 B 簇；卷 0 MFT 11,139 条记录 |
| 访问方式 | `CreateFileW(GENERIC_READ)` + `FILE_FLAG_NO_BUFFERING\|FILE_FLAG_OVERLAPPED`，提权 Full 令牌；全程零写入 |
| 工具链 | `build-gcc14`（MSYS2 GCC 14.2.0，Release），`PHOENIX_BUILD_REALDISK_TOOLS=ON` |
| 通道 | **仅结构化 MFT 通道**（`NtfsParser` + `RecoverEngine`），**未启用 RAW 雕刻** |
| 双份读 | 引擎恢复读一遍源盘；独立 `mft_oracle.py` 再读一遍算真值 SHA-256，两者字节逐文件比对 |
| 批 | 单批 24 GiB 预算，按 `firstLCN` 排序保证顺序 I/O；本节含 `batch_001`（9,233 文件 / 23.34 GiB）与 `batch_002`（619 文件 / 18.04 GiB） |

### 10.2 第 1–2 批实测（卷 0 全量）

吞吐统一按 `plan.json` 的精确 `bytes`（批 1 = 25,061,394,540 B，批 2 = 19,370,243,023 B）除以实测耗时，单位 **MiB/s**；早期草稿中 17.0 / 26.7「MB/s」为同一数据的十进制舍入，此处统一口径以便跨批比较。

| 阶段 | 批 1（9,233 文件 / 23.340 GiB） | 批 2（619 文件 / 18.040 GiB） |
|---|---|---|
| 引擎恢复 | 1372.2 s / **17.42 MiB/s** | 881.2 s / **20.96 MiB/s** |
| 独立 oracle 真值哈希 | 873.1 s / 27.37 MiB/s | 231.4 s / **79.83 MiB/s** |
| 逐文件对比 + 记录落盘 | 23.2 s | 27.6 s |
| 合计（含释放暂存） | 61.1 min | —（未单独计时） |

结果：**两批合计 9,852 文件 / 41.380 GiB，逐文件 SHA-256 与独立 oracle 100% 一致**，0 失败、0 误匹配、`badSectors=0`。批 1 有 4 个 `FileNode::id` 冲突额外节点（见诊断报告 §六-ter），批 2 为 0；额外节点单独记账，不影响召回。

**新增观察（支持 §10.4 瓶颈判断）**：批 2 只有 619 个文件（平均约 30 MiB/文件），oracle 真值哈希吞吐 **79.83 MiB/s**，是批 1（9,233 个小文件、27.37 MiB/s）的 2.9×；引擎侧也从 17.42 提升到 20.96 MiB/s。数据量相近而文件数差 15×，差异主要来自逐文件/逐簇的调用开销，而非磁盘顺序带宽。批次 3–6 的文件数达 10.6 万–46.6 万，预计该开销会更显著，待全量完成后复测。

### 10.3 顺序预读缓存 A/B（负面结果，**不启用**）

实现：`SectorReader::SetReadAheadWindow()` 默认关闭的滑动窗口（4096/扇区对齐、一次 `TryRead` 填充、失败透明回退），CTest `SectorReaderReadAhead` 23/23 + 源码级负向验证守护。

真实盘同一组 30 文件 / 87.8 MiB（按 `firstLCN` 排序）：

| 窗口 | 耗时 | 相对基线 | 预读填充 | 命中 |
|---|---:|---:|---:|---:|
| 0 MiB（基线，正式批次采用） | **6.26 s** | 1.00× | 0 | 0 |
| 4 MiB | 7.57 s | 1.21× | 262 | 21,216 |
| 32 MiB | 35.03 s | **5.60× 慢** | 186 | 21,292 |

原因：LCN 跨度 26 GiB、文件大小与碎片差异大，窗口频繁失效；32 MiB 时投机读累计约 5.8 GiB，而实际只需 ~99 MiB。**结论：该负载下预读是负优化，正式批次一律 `0`。** 代码与 CTest 保留仅作可复现的负面结论，默认关闭时字节/统计/回调语义与 GUI 路径完全一致。

### 10.4 瓶颈与边界（不得夸大）

- 瓶颈是调用粒度：`RecoverEngine::WriteRecoveredFile` 每簇（4096 B）一次 `ReadBytes` → `ReadSectors → TryRead`（overlapped `ReadFile` + 事件等待），全量约 3,500 万次；不是磁盘顺序带宽。有效方向应是按连续 run 合并读取（本轮未做，避免牵动生产恢复路径）。
- 本节**仅 2 批数据（卷 0）**，不是全量 6 批结论；非 GUI 端到端；不含真实坏扇区、碎片化极端场景的独立分层（本盘 `badSectors=0`）。
- **不能**据此给出真实卷误报率：RAW 雕刻通道未启用，真值是 MFT 解析而非用户文件清单。
- 口径与 §8（合成镜像吞吐）、§9（8 MiB 合成噪声误报率）**不可混用、不可跨机比较**；CPU/RAM/USB 桥接型号未采集。
- 本节是基线测量，不作发版门禁。
