# PhoenixRecover 首轮最小测试集

> 目标：用最少的测试成本，最快看出当前版本和第三方的核心差距。

---

## 1. 首轮只测这 3 个场景

### 场景 A：NTFS 正常卷基础对比

**为什么先测它**

- 当前主扫描链路首先要证明在最常见的 `NTFS` 场景下能稳定工作。
- 这个场景最容易看出“是否异步逐步出结果、是否会卡、数量是否离谱”。

**测试目标**

- 扫描是否能正常启动
- 首个文件是否快速出现
- 左树/右侧是否持续增量更新
- 总文件/文件夹数量是否和第三方差得太大
- UI 是否可操作

**建议数据条件**

- 系统外的一个普通数据盘，或非系统关键目录的逻辑卷
- 文件量建议在 `1 万 - 5 万`
- 同时有图片、文档、压缩包、视频

**本轮必须记录**

- 首个结果出现时间
- 扫描完成总耗时
- 总文件数
- 总文件夹数
- 是否卡顿
- 是否可停止

**通过线**

- 不崩溃
- 有持续出结果，不是最后一下子出来
- 数量虽然可有偏差，但不能明显离谱

---

### 场景 B：已删除文件样本对比

**为什么第二个测它**

- 你做的是恢复软件，光能扫出现有文件不够，必须尽快验证“已删除文件是否真的能回来”。
- 这个场景最容易暴露数量差异和结果质量差异。

**测试目标**

- 已删除样本能否被发现
- 路径、文件名、类型是否正确
- 与第三方相比是否明显漏扫

**建议数据条件**

先人工准备一小批样本，建议：

- 图片 10 个
- 文档 10 个
- 压缩包 5 个
- 视频 3 个
- 音频 5 个
- 若干不同层级目录

操作方式：

1. 先建立样本目录
2. 记录样本清单
3. 删除样本，但不要继续大量写盘覆盖
4. 分别用两边扫描

**本轮必须记录**

- 样本总数
- PhoenixRecover 找回数
- 第三方找回数
- 漏掉的是哪些样本
- 有没有重名、错路径、错类型

**通过线**

- 至少能稳定找回一部分明确已删除样本
- 不应出现大量明显错误路径或错误类型

---

### 场景 C：大结果量稳定性与交互对比

**为什么第三个测它**

- 你前面最核心的问题之一就是“点击扫描就卡、动态不出来、像整批加载”。
- 这个场景能最快验证这几轮“流式回调 + 增量 UI”改造是否真的有效。

**测试目标**

- 扫描中 UI 是否还可点击
- 左树是否持续增长
- 右侧是否持续追加
- 搜索/切换路径/切换类型时是否明显卡顿
- 停止按钮是否能响应

**建议数据条件**

- 文件量尽量大一些，建议 `5 万+`
- 多层级目录
- 小文件和图片混合

**本轮必须记录**

- 扫描中是否假死
- 左树是否滚动时卡顿
- 右侧列表是否频繁闪烁/整表重建感明显
- 点击停止后多久响应
- 是否崩溃

**通过线**

- 无明显假死
- 可点击
- 可停止
- 结果持续增加

---

## 2. 首轮执行顺序

就按下面顺序，不要打乱：

1. 先测 `场景 A`
2. 再测 `场景 B`
3. 最后测 `场景 C`

原因：

- `场景 A` 用来证明主链路是否可用
- `场景 B` 用来证明恢复价值是否成立
- `场景 C` 用来证明交互与稳定性是否过关

---

## 3. 首轮不用急着测的内容

这些先不要放进第一轮，避免分散精力：

- exFAT / FAT32 / ext4 全覆盖兼容性
- 坏扇区场景
- 格式化后重建目录能力
- 重构文件节点
- 预览能力完整度
- 恢复导出完整闭环

这些内容重要，但不适合当“第一轮最小集”。

---

## 4. 首轮结束后你最应该得到的结论

第一轮测试结束后，至少要回答清楚这 3 个问题：

1. 当前版本在 `NTFS` 下，扫描结果数量和第三方相比差多少。
2. 当前版本是否真的能发现“已删除文件”，还是主要只是把现有文件列出来。
3. 当前版本的扫描交互是否已经摆脱“卡死、整批刷、无法点击”的问题。

---

## 5. 首轮结束后的修复优先级建议

如果测试后问题很多，建议按这个顺序修：

1. 先修“扫描结果是否真的正确”
2. 再修“扫描过程是否稳定可交互”
3. 再修“数量差异”
4. 再做“性能优化”
5. 最后补“多文件系统兼容性”和“重构结果质量”
