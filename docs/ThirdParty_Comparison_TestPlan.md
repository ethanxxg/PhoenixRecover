# PhoenixRecover 第三方对比测试清单

> 目标：将 `PhoenixRecover` 与第三方恢复软件进行同盘、同数据、同环境对比，量化当前在“文件/文件夹数量、兼容性、稳定性、速度、结果质量”上的差距。

---

## 1. 测试目标

本清单重点回答以下问题：

1. 同一块盘扫描后，`PhoenixRecover` 与第三方工具在文件/文件夹数量上是否接近。
2. 不同文件系统、不同损坏程度、不同删除场景下，兼容性是否稳定。
3. 扫描过程中 UI 是否流畅，是否存在卡死、假死、崩溃、停止无响应。
4. 扫描速度是否可接受，和第三方差距处于什么量级。
5. 扫描结果中是否存在明显漏扫、重复、路径错误、类型错误、时间错误。

---

## 2. 对比原则

- 必须使用同一台机器。
- 必须使用同一块测试盘或同一个测试镜像。
- 必须保证两边扫描前测试数据一致。
- 每轮测试只改变一个变量，例如文件系统类型、数据量、删除方式、坏扇区场景。
- 若第三方工具支持更多附加能力，记录时要注明，不直接混为“数量差距”。

## 5. 推荐测试数据集

建议至少准备以下 5 组数据：

1. 小规模正常卷
- 1 万以内文件
- 目录层级较浅
- 混合图片/文档/视频

2. 中规模真实用户卷
- 5 万到 20 万文件
- 包含多层目录
- 含大量小文件

3. 已删除文件场景
- 删除后未覆盖
- 含不同类型文件
- 含批量删除和单文件删除

4. 格式化/重建目录场景
- 快速格式化后再扫描
- 检查目录恢复能力、类型聚合能力

5. 异常场景
- 坏扇区或可模拟的读失败场景
- 文件系统有轻微损坏
- 外接设备中途断开或权限异常

## 6. 测试用例清单

### Case 01：NTFS 正常卷基础对比

**目的**：验证最基础的数量、路径、速度差距。

步骤：
1. 选择同一个 `NTFS` 卷。
2. 在 `PhoenixRecover` 中发起扫描。
3. 记录首个结果出现时间、10%/50%/100% 时间、总文件数、总目录数。
4. 用第三方工具重复同样操作。
5. 对比总量与目录结构差异。

通过标准：
- 文件数量差距在可解释范围内。
- 不出现明显整批卡住后一次性冒结果。
- UI 在扫描中可操作。

### Case 02：已删除文件恢复数量对比

**目的**：验证删除文件发现能力。

步骤：
1. 在测试盘创建一批样本文件。
2. 记录样本清单。
3. 删除文件但不覆盖。
4. 分别用两边扫描。
5. 检查样本是否被发现、路径是否正确、类型是否正确。

记录表：

| 样本文件 | 类型 | 是否被 PhoenixRecover 找到 | 是否被第三方找到 | 路径是否正确 | 备注 |
|---|---|---|---|---|---|
|  |  |  |  |  |  |

### Case 03：大结果量稳定性对比

**目的**：验证海量文件下的稳定性与 UI 流畅度。

步骤：
1. 选择大数据卷。
2. 两边分别扫描。
3. 重点观察：
- 左树是否逐步增长
- 右侧列表是否逐步刷新
- 是否卡顿
- 是否能点击停止
- 内存是否持续异常上涨

### Case 04：类型树与路径树准确性对比

**目的**：验证扫描结果组织质量。

步骤：
1. 扫描完成后切换路径视图和类型视图。
2. 抽查多个目录和类型分类。
3. 检查右侧文件列表是否与左侧选择一致。
4. 与第三方同位置结果做抽样对比。

抽样建议：
- 顶层目录 5 个
- 深层目录 5 个
- 每种类型抽 10 个文件

### Case 05：停止与异常恢复

**目的**：验证运行期稳定性。

步骤：
1. 扫描过程中点击停止。
2. 观察停止响应时间。
3. 检查是否保留已有结果。
4. 再次启动同卷扫描，观察是否崩溃或状态残留。

## 7. 问题归类模板

发现差异后，按下面方式归类：

| 问题编号 | 分类 | 现象 | PhoenixRecover 结果 | 第三方结果 | 严重级别 | 初步判断 |
|---|---|---|---|---|---|---|
| COMP-001 | 数量差异 | 少扫目录 |  |  | 高 | 目录枚举缺失 |
| COMP-002 | 兼容性 | exFAT 结果异常 |  |  | 高 | parser 兼容不足 |
| COMP-003 | 稳定性 | 扫描中 UI 卡顿 |  |  | 高 | UI 增量刷新仍不够细 |
| COMP-004 | 性能 | 首屏结果慢 |  |  | 中 | 扫描线程/回调链路耗时 |
| COMP-005 | 结果质量 | 路径错误/重复 |  |  | 中 | 去重/重建策略不足 |

分类建议：
- `数量差异`
- `兼容性`
- `稳定性`
- `性能`
- `结果质量`
- `UI 同步`

## 8. 判定建议

### 8.1 当前阶段可接受标准

在当前开发阶段，可以先以以下标准作为“可继续推进”的门槛：

- 主流 `NTFS` 卷能稳定扫描，不崩溃。
- 首个文件能较快出现，且结果为逐步增加，不是最后一次性出现。
- 文件/文件夹总量与第三方相比，偏差可控且能解释。
- 路径视图、类型视图切换后结果基本一致。
- 停止扫描可响应。

### 8.2 真正对标第三方的目标标准

后续若要宣称“接近第三方”，建议至少达到：

- 主流文件系统下扫描结果数量差距较小。
- 删除文件样本找回率稳定。
- 大数据量扫描 UI 不明显卡顿。
- 异常卷、坏扇区、长路径场景下不易崩溃。
- 结果去重、目录结构、类型归类、预览可用性接近第三方。

---

## 9. 建议执行顺序

建议按以下顺序测试：

1. `NTFS 正常卷基础对比`
2. `已删除文件场景`
3. `大结果量稳定性`
4. `类型树/路径树准确性`
5. `异常与停止响应`
6. `exFAT/FAT32/ext4` 兼容性补测

---

## 10. 首轮输出物

首轮测试结束后，建议至少产出这 3 份结果：

1. 一份完整填写后的本测试表。
2. 一份“PhoenixRecover vs 第三方差异 Top 10”问题列表。
3. 一份按优先级排序的修复计划：
- 先修数量差异
- 再修稳定性
- 再做性能优化
- 最后补异常场景和重构结果质量
